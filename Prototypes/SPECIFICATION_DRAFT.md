# Experimental OTIO multicam interchange: draft semantics v1.4

> **AI generation disclosure.** This proposal, its code, tests, examples and documentation were generated by **ChatGPT (OpenAI)** through an iterative discussion. The project contributor supplied or identified real Avid AAF, Premiere Pro and DaVinci Resolve examples, specified editing requirements, corrected assumptions (including one fixed angle choice per edit), and ran and reported integration tests on a Mac. Passing the reported tests does **not** establish that an NLE can import the extension, that the schema is suitable for inclusion in OTIO, or that the code has been independently reviewed. The maintainer community has substantially deeper expertise in OTIO architecture and should be invited to challenge, replace or simplify this design.

**Status:** exploratory *SchemaDef* proof of concept, **not** an approved OTIO schema or specification. No claim of direct compatibility with existing host importers.

## Scope and terminology

- **Definition:** a reusable identity describing one multicam, ordinary nested sequence or compositing definition. Definitions contain picture/audio outputs, angle order and internal structure; they are not timeline edit instances.
- **Occurrence:** a reference to one definition with its own source/timeline timing and stable occurrence identifier. Several occurrences may share one definition without mutating it.
- **Selector:** one fixed output choice for one continuous edit segment; changing a picture or audio source requires an edit boundary *in that stream*. Audio and video may cut at different frames. An embedded child multicam has its *own* edits within its definition, independent of parent edit boundaries.
- **Angle identity:** positive integer local to `(definition_id, group_id)`; distinct from display order and native AAF slot number. An angle may reference a media output, another multicam occurrence, or a composite output.
- **Output:** explicit, typed picture/audio/alpha output reference or composite port. A graphics fill/key nest may yield one RGBA picture output from two separate inputs. Multiple uses of one source are valid.
- **Media identity:** relinkable source record with original paths/locators, source MobIDs, timecodes and channel provenance; these are not automatically verified filesystem locations.

## Current experimental classes

`MulticamPackage.1`, `CompositionDefinition.1`, `CompositionReference.1`, `MulticamSelector.1`, `AngleDefinition.1`, `OutputReference.1`, `CompositeOperation.1`, `CompositeOutput.1`, `RelinkableMedia.1`.

A `MulticamPackage` wraps a conventional OTIO `Timeline` plus a shared registry of typed definitions and occurrences. **This packaging is a design hypothesis**, not an assertion that a custom root object is the best OTIO integration point. Maintainers may prefer extending standard `Clip`/`MediaReference`, a separate companion interchange payload, or existing OTIO composition primitives.

## Normative *candidate* constraints (open to change)

1. Namespaced IDs must be unique in their declared scope; `(definition_id, group_id, angle_id)` identifies a portable angle. An `output_ref_id` is **not** a unique angle ID: multiple angles may refer to the same source output.
2. A fixed video/audio selector is constant throughout its edit segment. Independent picture/audio edits preserve their original boundaries; a derived combined-interval view must not insert cuts into the underlying tracks.
3. Source reference timing is represented separately from source-timecode labels. Frame-rate conversions use rational arithmetic; gaps remain gaps. Current v1.3 resolver does **not** fully implement these timing semantics.
4. A parent may select a nested composition's output without copying the nested definition. Repeated occurrences must have distinct occurrence identifiers and may carry independent per-occurrence nested selections.
5. Graphics composites encode named input roles (fill/matte), alpha assumptions, output alpha type and operation provenance. Current composite fixture is symbolic only, not portable rendered-effect equivalence.
6. Reference cycles, duplicate identity keys, unresolvable selections and missing essential outputs must fail explicit validation. Unknown extensions may be preserved opaquely but must not be silently discarded when claiming lossless interchange.
7. Relinking is independent from source identity. Paths, tape/reel and timecode are candidate matching evidence; ambiguity must be reported, not guessed.
8. A host that cannot reconstruct an editable multicam or composite must not claim a lossless/native import. Flattening is optional and must be disclosed, with a reproducible mapping/rendered derivative if visual fidelity is claimed.

## Cross-application evidence, with caveats

- **Avid AAF example:** contains native AAF Selector alternatives and 59-slot backing composition, edited picture and independently edited audio, plus nested graphics effects. The typed experimental fixture maps 79 selector objects; 60 edited selector clips; three compositions; 16 media records. A simplified newly authored *offline-placeholder* AAF was generated and read back with `pyaaf2`; this does not prove Avid recognises it as native editable multicam.
- **Premiere Pro project:** native project parser found reusable sequence-to-sequence references including spatial two-/three-/four-box layouts. Camera choice reconstruction and exact effects semantics remain incomplete.
- **DaVinci Resolve DRT:** native multicam/compound identity and repeated references were extracted; not all internal container ownership or selected-angle fields were decoded.
- **Mac OpenTimelineIO validation:** user reported v1.3's 24 unit tests passing and both Avid-derived and synthetic recursive typed fixtures successfully completing OTIO `read/write/read`. This establishes preservation through *that installed OTIO runtime and plugin*, not an upstream implementation or generic host importability.

## Consumer adapter policy

Use `CAPABILITIES.json` as a proposed vocabulary. A consumer must make an explicit capability assessment before choosing **native editable reconstruction**, **structural preservation with unsupported features**, **opt-in lossy translation**, or **rejection**. The availability of a standard `Timeline` in the package is *not* evidence that complex multicam operations have been translated.

Example diagnostics:

```
UNSUPPORTED_NATIVE: external_matte at GRAPHICS/OUT_GRAPHICS
UNSUPPORTED_NATIVE: occurrence_local_nested_selections at edit_2/outer_quad/quad_TR
MISSING_DERIVATIVE: cannot offer visually faithful flatten without rendering or equivalent effect mapping
MEDIA_AMBIGUOUS: source candidate requires confirmation
```

## Tests and limitations

`python -m unittest discover -p 'test*.py' -v` runs source package tests plus conformance checks. `OTIO_PLUGIN_MANIFEST_PATH="$PWD/manifest.json" python check_v13_runtime.py` is the existing native OTIO smoke test. These are *separate* proofs: syntactic schema conformance, symbolic interpretation, OTIO serialisation, AAF authoring, and NLE reconstruction.

Not proven: a full AAF ↔ OTIO ↔ AAF structural equivalence; native NLE round-trip of compound effects; sample-accurate audio, varying-speed media, arbitrary frame-rate resampling, fill/key pixel fidelity, full nested time propagation; schema-plugin support in third-party importers.

## Questions for maintainers

1. Is a registered `SchemaDef` root plus shared registry appropriate, or should references be ordinary `Clip`/`MediaReference` extensions or externally stored definitions?
2. Which OTIO composition, transition, effect and media-source constructs should we reuse to avoid duplicating core concepts?
3. How should typed selectors and stable angle identities relate to OTIO's timeline event semantics and `Track` structure?
4. What is the preferred serialization/identity approach for repeated shared definitions and nested per-occurrence state?
5. Which common effect semantics—external matte, alpha, spatial grid—belong in OTIO versus host-specific metadata?
6. What is the recommended progressive-fallback model when host adapters cannot round-trip all nested editable semantics?
7. Which portions could be proposed as narrow upstream enhancements versus remaining a specialized optional plugin?

**Request:** architectural critique and pointers to existing OTIO capabilities before considering API adoption. The generated implementation is offered as a *testable example of requirements*, not as a preferred or production-quality upstream design.
